# Portfolio configuration form and API — specification s001

Proposed 2026-11-04 (America/Sao_Paulo); approval pending with plan p001. This describes form capture only; no investment or backtest calculation is defined.

## Goal and scope

Place a portfolio configuration form beside the existing chart, load the four available indexes from FastAPI using Axios, let users choose allocations that total exactly 100%, capture dates and a rebalancing choice, and submit the configuration to a second FastAPI route that acknowledges it. The existing chart remains an illustrative example with its disclosure; submitting the form does not affect it.

## Proposed interaction

- On successful index loading, show IBOVESPA, IFIX, Selic and S&P 500 as selected, each with 25.00%. Selecting or deselecting an index resets the selected indexes to equal shares, distributing any hundredth-of-a-percent remainder deterministically in API order. At least one index remains selected. Unselected indexes have no allocation and are omitted from submission.
- Each selected index has a labeled slider and editable percentage field, supporting values from 0 to 100 to two decimal places. Changing one allocation adjusts the other selected, unlocked allocations proportionally to their current shares; if their total is zero, divide the remainder equally among them. Optional labeled locks keep chosen shares fixed so users can set any desired allocation one share at a time; at least one other selected share must be unlocked to change a value. The input's permitted maximum reflects locked shares, and toggling selection clears locks. Use integer hundredths of a percent and allocate rounding remainder by largest fractional remainder, using API order to break ties, so committed allocations always total exactly 100.00%. With only one selected, its allocation is 100%; a selected index may have zero. The UI explains adjustment, locking and that changing the selection resets shares equally. Editing a field may temporarily leave an incomplete text value, but the last committed allocation remains valid; reject or restore invalid input with an accessible message.
- Capture required initial and end dates, default blank, as calendar dates. Both must be valid and the initial date must be on or before the end date. No restrictions on available history, non-trading days or future dates are inferred.
- Provide a native rebalancing selector with None (default), 3 months, 6 months, 1 year, 2 years and 3 years. These are stored request labels only; execution timing and financial meaning remain undecided.
- Show loading, retryable index loading error, pending submission, acknowledgement and retryable submission error states. Validate dates and allocation before submitting, prevent duplicate requests while pending and clear a stale acknowledgement when the form changes. Do not describe acknowledgement as a saved or calculated backtest.

## API contract

- `GET /api/indexes` returns HTTP 200 and exactly the ordered JSON array `[{"id":"ibovespa","name":"IBOVESPA"},{"id":"ifix","name":"IFIX"},{"id":"selic","name":"Selic"},{"id":"sp500","name":"S&P 500"}]`.
- `POST /api/portfolio` receives JSON such as `{"initial_date":"2020-01-01","end_date":"2024-12-31","allocations":[{"index":"ibovespa","percentage":40},{"index":"sp500","percentage":60}],"rebalancing":"6_months"}`. Dates use valid `YYYY-MM-DD` strings in order. Allocations contain one to four distinct known IDs, each percentage is a JSON number from 0 through 100 with at most two decimal places, and their exact decimal sum is 100. Valid rebalancing values are `none`, `3_months`, `6_months`, `1_year`, `2_years` and `3_years`. A valid request returns HTTP 200 and exactly `{"status":"ok"}`. Invalid, missing, duplicated or unknown fields/values, invalid dates, or allocations that do not total 100 receive HTTP 422; they are not acknowledged as valid.
- No persistence, data acquisition, file access, portfolio calculation or result generation is performed. Import and backend startup do not make network requests. `/health` continues to work.

## Acceptance criteria

- **AC-001 — Index route and load:** The index route returns the exact four names and stable IDs above. The frontend uses Axios to fetch the route, shows loading and a recoverable error for network, HTTP or malformed response failures, and only presents a working form after a valid response. Reload and retry work without substituting fabricated indexes.
- **AC-002 — Allocations:** Initial shares are 25% each. Users can choose one through four indexes and reach any valid two-decimal allocation, including 100% in one index and a two-index split. Locks preserve fixed shares until unlocked; a user can set an arbitrary four-index allocation by locking each finished share and adjusting the remaining shares. The committed shares always total exactly 100.00% during selection, slider and valid field interactions, including rounding and zero-share edge cases; the visible total agrees. Invalid/incomplete edits do not corrupt committed shares. Controls, labels and status are keyboard operable and accessible.
- **AC-003 — Dates and strategy:** The form has labeled initial/end date fields and the six specified strategy choices with None selected by default. Empty, invalid or reversed dates prevent submission with understandable feedback; an ordered equal-date pair is accepted. No dataset-availability rules are introduced.
- **AC-004 — Submission:** Valid user choices are sent via Axios using the specified contract. The route acknowledges valid one-, two- and four-index inputs with the exact status body, rejects invalid payloads with 422, and performs no calculation or persistence. The UI indicates pending, success and error accurately, avoids duplicate requests and allows retry.
- **AC-005 — Integrated presentation:** At 1280 px viewport width the form is side by side with the existing chart, both readable without clipping or page-level horizontal overflow, including the chart's open data disclosure. At 768 px the panels stack or otherwise remain readable without page-level horizontal overflow. The chart remains visibly identified as illustrative; submission does not update it or suggest a result was calculated. The previously accepted 320 px limitation is outside this feature's acceptance scope.
- **AC-006 — Boundaries and usage:** The health endpoint and existing chart behavior remain intact; no market data files, acquisition or domain calculation change. Document installation, both servers, proxy, production integration assumption, endpoint contract and current acknowledgement-only behavior. Backend code follows `backend/AGENTS.md`, frontend code follows `frontend/AGENTS.md`, and dependencies are declared in their existing manifests and lockfile as applicable.

## Decisions and exclusions

The user's request establishes the four available choices, equal default weighting, exact 100% allocation, ability to select one or two indexes, date fields, the six strategy options and acknowledgement-only submission. The interaction details, request contract, validation, precision and responsive widths above are proposed for approval. Weights are configuration inputs, not a definition of holdings, currencies, returns, Selic treatment or rebalancing timing. Historical data alignment, data date validation, persistence, results, authentication and deployment are excluded.
