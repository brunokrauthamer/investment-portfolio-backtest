# IFIX daily-evolution acquisition — plan p001

Status: proposed on 2026-11-03 against specification s001; awaiting explicit human approval of both revisions. No implementation has begun.

## Architecture and boundaries

- `backend/src/acquisition/`: an IFIX-specific source adapter discovers offered period identifiers and retrieves the actual B3 downloads through the documented site flow. Use a browser automation adapter (Python Playwright) if the page requires it; only use a direct source download endpoint if inspection confirms it is the same original download. The concrete selectors, period mapping and validation rules must be grounded in source inspection, not invented. Timeouts, pacing, error classification and TLS verification live at this boundary.
- `backend/src/application/`: the acquisition operation requests the available periods, coordinates each download and storage result, and returns a complete/partial summary and exit status. Periods are distinct source identifiers, not assumed years. Processing one failure must not destroy other periods' files.
- `backend/src/storage/`: a focused local adapter maps periods to safe stable filenames, compares bytes/hash, creates and verifies external backups before changed replacements, stages sibling temporary files, uses atomic replace, owns the exclusive lock, and keeps a manifest atomically. Never trust a remote filename as a path. The manifest is metadata, not a new market data series. Recoverable crash handling must not falsely mark an incomplete run successful.
- A small explicit command entry point assembles the dependencies. Proposed invocation from the project root: `python -m backend.src.acquisition.ifix` after installing the documented dependencies; validate the actual command in integrated tests. No calls on imports/startup. Use standard Python modules where sufficient; the browser dependency is justified by potentially dynamic site interaction and is conditional on source inspection.
- Separate source, orchestration and storage because their failure modes and responsibilities differ; do not add generic provider/plugin frameworks. Unresolved page mechanics are isolated within the IFIX adapter.

## Ordered implementation and evidence

1. **Source discovery gate:** inspect the actual page and download flow using available allowed tooling; record the selected periods, download filename/format, representative earliest and latest available periods, response validation, access constraints, and any limitation. Check applicable B3 terms without assuming that notices on other pages apply. Resolve material conflicts with this spec through revised human-approved records before implementation. Do not circumvent access restrictions. If access is unavailable, record the blocker and do not claim live evidence.
2. **One initial implementation round with TDD:** developer writes failing tests then implementation for source-period discovery, orchestration, CLI, exact-byte storage and provenance. Tests use controlled responses and dummy non-market bytes. Cover 2011 through latest source-offered period and a changing latest period; source error, missing/ambiguous discovery, invalid response, timeout; distinct periods with duplicate source filenames.
3. **Safe updates:** test-first atomic active writes, same-byte no-op, verified recoverable backups, backup/replace failures, crash-safe recovery and overlapping commands. Document the supported filesystem/locking semantics. Test backup restoration and verify unchanged file modification time.
4. **Documentation and integration:** document installation (including any browser runtime), command, layout, source origin, terms actually observed and personal-use context, run output, limitations and restore steps in relevant backend/data project docs. Do not commit downloaded B3 data unless explicitly requested. Run the documented command and the complete automated checks. Any real-source failure remains explicit.
5. **Independent review and QA:** an independent reviewer checks approved spec, architecture, code, tests, documentation and exact integrated snapshot; independent QA executes every criterion and adverse case, including a source-backed end-to-end check when permitted and available. This is a command-line feature with no user-facing web feature, so browser QA of a project UI is not applicable; browser interaction with B3 may be needed to verify source behavior. Capture outputs, environment, coverage and limitations, and snapshot identity before/after each evaluation. Record TDD red/green/refactor evidence in `verification.md` and findings in `review.md`.
6. **Final audit:** lead verifies fresh independent review/QA, no unresolved blockers, exact revision/hash and snapshot evidence, documentation and checks. Then request explicit final approval; approval does not authorize commit, publication or deployment.

## Risks and alternatives

B3 can alter controls, file formats, availability or usage conditions. A selector or source endpoint chosen without inspection would be speculative, so source inspection is an implementation gate. Browser automation has runtime and maintenance costs; use it only where justified by actual source behavior. A mock-only test cannot establish real coverage. Partial runs must report failure while keeping safely completed periods; source network and browser tool limitations are blockers for source-backed evidence, not assumed passes.
