# Selic daily acquisition — plan p001

Status: proposed 2026-11-03, paired with specification s001; no implementation until explicit human approval of both revisions.

## Architecture and interfaces

Create an asset-specific `backend/src/internet_data_getter/selic/` package. A source adapter uses Python Playwright and its Chromium browser to operate the actual SGS chart and paginated table, with bounded timeouts, TLS verification, paced navigation, and no access-control bypass. It returns validated textual date/rate observations plus source metadata; no parsing or browser activity occurs on import. A focused service orchestrates extraction, completeness checks and storage and returns a report compatible with the existing registry. A storage component owns CSV generation, lock, hash-verified backups, write-ahead transaction and recovery, atomic active-file/manifest updates and offline restore. Reuse established IFIX storage code only where an actual common contract can be preserved safely; avoid forcing incompatible source formats or introducing speculative generic layers. Add the getter to the shared Python and CLI registry without changing IFIX behavior. Offer a documented Selic-specific restore entry point without making the existing IFIX restore ambiguous.

Browser automation is proposed because the request explicitly specifies manipulating chart controls and paging; a direct API or alternative download endpoint would change that behavior. Keep the browser adapter behind a small injectable boundary so offline tests can exercise orchestration and malformed page responses without network or real market fixtures. Verify actual page DOM and form/session behavior during implementation; if it cannot meet approved criteria, stop and report rather than silently change source behavior. `backend/requirements.txt` declares Python dependencies; document the Playwright Chromium installation as a separate setup step and its constraints.

## Risks and alternatives

BCB's paginated interface, browser dependencies and metadata can change or become unavailable, and displayed precision and completeness depend on the source. Validate source labels and count on every run; fail safely when they are unclear. A multi-file commit is not intrinsically atomic, so the write-ahead record, verified backups and explicit recovery are required. Source data can be revised while pages are traversed; reject contradictory metadata/counts, but a source that silently changes values while preserving count may remain undetectable and must be documented. The existing official JSON/CSV endpoint is not a substitute without user approval because the requested workflow explicitly specifies chart interaction; the BCB dataset page also documents a 10-year maximum per JSON/CSV query. No synthetic market data or return calculations are introduced.
